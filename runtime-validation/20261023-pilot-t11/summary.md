# T11 pilot: support multiple Codex input channels

Both T11 conditions passed the frozen host-owned acceptance. The v1 patch passed 62 project tests; v2 passed 63. Independent graders rebuilt fresh wheels from the pinned snapshot, installed offline, and passed all five semantic checks: primary plus listed channels forward once, unlisted channels are ignored, legacy configuration remains valid, malformed lists raise `ConfigError`, and replies still target `CODEX_CHANNEL_ID`.

The v1 security review found that an invalid channel value could be echoed in a configuration error. The raw value was removed, covered by a regression test, and the final patch passed code, test, and security reviews. The v2 code review found that empty entries inside a nonempty list were accepted; those are now rejected, with whitespace-only configuration retaining legacy behavior. The final v2 patch passed code and security reviews. The external project snapshot has no `scripts/harness.py`, so candidate-side Harness full-check and risk commands could not run.

The pair ran v2 then v1 (TUI-reported 3m32s and 6m27s). A fresh `/new` conversation was confirmed before each condition, the candidate was reset to the same pinned baseline, and both used identical task/prompt hashes. The TUI process itself was reused. The TUI parent ran on the host; only tool children used `harness-eval`. Exact thread IDs, token usage, shell-command counts, and subagent-turn counts were unavailable. The v1 TUI could not read system Git configuration during Git status/diff inspection; no candidate branch or commit was attempted, and the patch was extracted read-only for independent host grading. No candidate-initiated live service call, push, publication, or merge occurred.
